# F32 — Project map

`/map` draws the repository as a picture the user can rearrange: plates for the
things a maintainer would name out loud, grouped into layers, joined by lines
whose dash and arrow head say what the relationship is. The drawing is
`.openhands/project-map.json` in the workspace, committed with the code, so the
arrangement is part of the repository and the agent can edit it too. The page
reads that file through the typed client's file routes, keeps an editor buffer
over it (drag, rename, hide, pin, regroup, note, collapse), and writes it back
only when the user presses **Save map**. A **Repository** picker says which
folder the map is a picture of. A map with more parts than a person can read at
once opens as its layers — a block each, with how many parts it holds and the
folders those parts live in — and a click opens one. Beside the canvas a rail,
folded until asked for, reads the selected node, walks its edges and holds the
key to the drawing; in the canvas's corner a chat dock, folded until asked for,
turns the selection into the first message of a conversation that stays bound
beside the map. With no file yet the page explains what a project map is, asks
which repository, and offers to start the analysis conversation, which it keeps
rather than leaving for. On a Cloud backend, or with no backend, it reports the
map as unsupported instead.

Source: `src/routes/map.tsx`, `src/components/features/project-map/`, `src/api/project-map-service/`, `src/hooks/query/use-project-map.ts`, `src/hooks/mutation/use-save-project-map.ts`, `src/stores/project-map-store.ts`, `src/stores/project-map-workspace-store.ts`, `src/utils/project-map/`, `src/types/project-map.ts`, `src/prompts/project-map-analysis.md`.

## Sub-features

- `F32.open`: the sidebar's **Project map** entry (`sidebar-map-link`) and the URL `/map` open a page headed `Project map`, whose sentence `A picture of the repository's code: what talks to what, in layers you can rearrange.` explains a picture while there is none to look at and gets out of the way once there is: it is a paragraph under the heading in the empty state and the notices, and over a drawn map it is the heading's hover alone (the `h2`'s `title`, which carries it in every state). The page also has the header controls **Fit to view**, **Show hidden nodes** (`project-map-show-hidden`), **Reload from file** (`project-map-refresh`), **Rebuild with the agent** (`project-map-regenerate`) and **Save map** (`project-map-save`) once a document is open. Each of them, and the provenance line, says on hover what it does (a `title`); the **Repository** picker (`project-map-workspace-picker`) names the folder the map was read from — its last segment in the field, the whole path in `data-path` and on hover (`title`) — rather than showing `Choose a repository…` beside a map, and over a drawn map it is the only thing that names it: the `Workspace: …` line (`project-map-workspace`) is left to what the picker cannot say, a conversation bound to the page or a backend with no picker; and the switch rows over the canvas are captioned `View` (Overview/Details, `project-map-view-switch`, offered whenever the drawing on the paper has at least two layers), `Show` (Analysis/Drawing/Both, `project-map-mode-switch`) and `Map of` (Code/Work, `project-map-layer-switch`), every choice in them with a hover hint of its own, and last in that group the rail's own toggle (`project-map-rail-toggle`), which reads `Details` while the rail is folded — the state the page opens in.
- `F32.command-menu`: the command menu's `Project map` / `See what talks to what in this repository` item (`command-menu-option-map`, Navigation group) opens the page.
- `F32.empty`: with no `.openhands/project-map.json` the page shows `No project map yet` (`project-map-empty`), the paragraph explaining that the map is a file in the repository, the **Repository** picker (`project-map-workspace-picker`) with its hint, `The map is drawn from a folder on this machine. Choose one of your saved workspaces, or add the folder that holds the repository.`, and **Generate the map** — and no header controls at all. This is where the page explains itself in words: the subtitle is a paragraph under the heading, and `project-map-workspace` says which directory was read (`Workspace: Local — <path>`). With a folder chosen in the picker that has no map, the title names it (`No map of <folder> yet`, the folder's last path segment), a second paragraph (`project-map-empty-other-maps`) says `Your other maps are where they were: each lives in its own repository. Pick one in the Repository list above to see it again.`, and the picker sits in the header instead — taking the `Workspace:` line with it, since the picker's own `data-path` and hover say that folder once. The subtitle stays prose throughout: nothing is drawn yet.
- `F32.generate`: **Generate the map** starts a conversation whose first message is `src/prompts/project-map-analysis.md` verbatim, closed by the absolute path to write the map to, and keeps it instead of leaving for it: the empty state then reads `Conversation <id> is building the map in <path>. It appears here as soon as the file is written.` (`project-map-analysis-running`) with **Reload from file** (`project-map-empty-refresh`) and **Open full screen** (`project-map-empty-open-conversation`), and the drawing appears by itself once the agent's edit of that file is reported.
- `F32.drawing`: every visible node is a plate (`project-map-node-<id>`, `role=button`, accessible name `<Kind> <label>`); a plate tall enough also carries its path under the label; each group draws a dashed boundary broken for its label (`project-map-group-<id>`); edges are `project-map-edge-<from>|<to>|<kind>` groups under the plates; a note is a boxed remark on a leader line (`project-map-note-<id>`).
- `F32.overview`: **View** → **Overview** (`project-map-view-overview`) draws the map's layers instead of its parts: a block per layer (`project-map-overview-block-<id>`, `role=button`, accessible name `<layer> — Open this layer`) carrying the layer's label, `<n> parts` (also `data-count`) and, under them, where those parts live (`data-where`) — the folder the layer's parts share and, inside it, the fullest entries, folders before files, as `src/{components/, hooks/, routes/}`, with the folders every path in the document shares stripped first and nothing named for a layer with no parts; a line per direction between two layers carrying how many relations run that way (`project-map-overview-link-<from>><to>`, whose hover title says it in words); `<n> more parts belong to no layer` (`project-map-overview-ungrouped`); and the hint `Each block is a layer of the code, with how many parts it holds. Lines show how many relations run between layers. Click a layer to open it.` (`project-map-overview-hint`) on the paper. Clicking a block leaves the overview and opens that layer, close enough to read. A map with more than 40 visible parts and at least two layers opens this way by itself, and then carries **All layers** (`project-map-all-layers`) on the paper as the way back up.
- `F32.layer-switch`: **Map of** (`project-map-layer-switch`) says which derived layer is on the paper — **Code**, the committed analysis, or **Work**, the live graph — and it is a view of this session's, like **View** and **Show hidden nodes**, rather than a fact about the repository. Switching writes nothing: `project-map-unsaved` stays absent, **Save map** stays `Saved`, **Undo** (`project-map-undo`) stays disabled, an edit already in hand is neither saved nor dropped by the excursion, and a save made afterwards adds no `canvas` block to a file that never carried one. A document that does name a layer (`canvas.view.layer`) opens on it, and keeps that line through a switch and a later save.
- `F32.work`: **Map of** → **Work** puts the live work graph on the paper in place of the analysis's parts: the machines Canvas is registered with, the programs on them, the runs those programs schedule, the cycles the runs claim, the agents, the repositories, the branches and pull requests and commits, the sources the agents read and the suggestions they made — each drawn with a silhouette the code map already has (a cycle as a module, an agent as a service, a repository as a directory, a run as a job). The plates keep the graph's own keys, `project-map-node-oh:<schema>/<backend>/<kind>:<id>`, which carry the deployment's host, so they are read by prefix rather than by name. None of it is in the file: no group boundary is drawn, `project-map-work-omissions` (`Some work is not shown. Open the inspector on a node to see why.`) says when a deployment left something out, and the rail stays with the analysis — selecting a work plate opens the rail, but `project-map-inspector-empty` is still what it holds and the legend still lists the committed document's kinds.
- `F32.work-layers`: the work graph carries its own layers, one per kind of work present, in the order the columns are drawn and named for a reader rather than for the schema — `Machines`, `Programs`, `Runs`, `Runs whose sandbox is gone`, `Cycles`, `Agents`, `Branches, pull requests, commits`, `Repositories`, `Sources the agents read`, `Suggestions` — so the fold into layers works on it too. The **View** row is offered whenever the drawing on the paper has two layers or more, **Overview** draws a block per kind (`project-map-overview-block-<kind>`, `role=button`, `data-count`, accessible name `<label> — Open this layer`) with how many relations run between kinds on the lines, every part belongs to a layer so none is named as belonging to none, and a click opens that kind's column. Switching layer frames what you switched to once the graph has settled — folded when it is a wall, more than 40 parts, and whole when it is not — and none of it reaches the document: the work layer's layers are assembled on every fetch, and only the committed analysis has groups a person can fold.
- `F32.rail`: the rail beside the canvas — a feature introducing itself, anything waiting on a person, the selection inspector and the key to the drawing — is folded until **Details** (`project-map-rail-toggle`, `aria-expanded`, hovering `The part you clicked, the key to the drawing, and anything waiting on you. Hidden, the map has the whole page.`) opens it, when the button becomes **Hide details** and the drawing gives up a quarter of the width to it. It opens itself for a selection and for a `/map` feature that has not introduced itself yet, and `data-waiting` carries the number of parked improvement cycles, the label becoming `<n> waiting on you` in warning colour when anything is parked.
- `F32.waiting-marks`: what the rail counts is also on the drawing. A part whose path a parked improvement cycle names in its own words — its summary, its parked question, or its changeover plan's breaks, consumers, sequence or rollback — carries `data-waiting="true"` and a warning-coloured dot (`project-map-waiting-mark`) whose hover reads `A change waiting on you touches this part.`; in the folded view the layer holding such parts carries `data-waiting="<n>"` and a dot of its own, reading `1 part here is in a change waiting on you.` or `<n> parts here are in a change waiting on you.` Only a change about the folder this map is of counts: that folder's name has to be in the cycle's repository label or URL, so another repository's change marks nothing here even when the two name the same file. Clicking a marked part selects it, and a selection opens the rail, which is where the card that answers it is.
- `F32.legend`: **Legend** (`project-map-legend`, in the rail, a disclosure open by default) draws the silhouettes and line styles this document actually uses, in the document format's order, and leaves out the kinds it does not.
- `F32.provenance`: the header reads `From commit <commit>, <when>` from the document's `commit` and `generated_at` (`project-map-provenance`; `<when>` is how long ago the analysis was made — `5h ago`, `2d ago`, or the date once it is a week old), `From commit <commit>` when `generated_at` is missing or not a usable timestamp, or `No commit recorded` when there is no commit; on hover it says the analysis was made from that commit and the code may have moved on since.
- `F32.select`: clicking a plate selects it (`data-selected="true"`, crop marks) and moves focus to it; the selection and everything wired to it stay at `opacity="1"` and every other plate fades to `0.18`; clicking empty paper puts the selection down and takes focus to the canvas.
- `F32.inspector`: the selection panel in the rail reads `Click a part of the map to read what it is and what it connects to.` (`project-map-inspector-empty`) until something is selected, then shows the node's kind, label, path and summary, `No summary yet. Ask the agent to describe it, or write one in the file.` for an empty one, and the actions **Rename**, **Hide**, **Pin where it is** and **Add a note**. The path is shown, not opened: the Files browser is a view of one conversation's sandbox and this page has no conversation.
- `F32.edge-lists`: `USED BY` (`project-map-inbound`) and `USES` (`project-map-outbound`) list one row per edge as `<kind> <label>`, each row selects the node at its far end, and a node with no edges reads `Nothing in the map connects to this yet.`
- `F32.multi-select`: shift-clicking or Meta-clicking a second plate adds it, and shift-clicking one already in the selection takes it back out; the inspector becomes a list of the selected nodes (`project-map-inspector-multi`) whose rows narrow the selection back to one, as does a plain click on any plate in it.
- `F32.marquee`: shift-dragging the paper sweeps a selection rectangle (`project-map-marquee`) and selects every plate it touched; a sweep that touches nothing clears the selection.
- `F32.keyboard`: every plate is a tab stop; the arrow keys move focus to the nearest plate in that direction, Enter selects it, shift+Enter adds it to the selection and Escape clears the selection. A mouse press leaves Escape working, because it moves focus into the canvas itself.
- `F32.pan-zoom`: dragging the paper pans it one-to-one with the pointer, however many moves the drag arrives in, without touching the document; the wheel zooms about the pointer between 0.25 and 2.5, and below 0.62 the dot grid and the plates' path lines stop being drawn.
- `F32.fit`: **Fit to view** frames the whole drawing, and the page does it once by itself when a document first arrives.
- `F32.move`: dragging a plate moves it on a 20-unit grid, pins it, and marks the document unsaved (`project-map-unsaved`, `Unsaved changes`); dropping it inside another group's boundary joins that group.
- `F32.rename`: **Rename** opens a field over the label; Enter commits it and the new label is the user's, so a later analysis keeps it.
- `F32.hide`: **Hide** takes a node out of the drawing with its edges; **Show hidden nodes** in the header (`aria-pressed`) draws hidden nodes again, dashed, so they can be restored.
- `F32.pin`: **Pin where it is** adds the drafting tick to the plate and the button becomes **Unpin**.
- `F32.regroup`: the `GROUP` select (`project-map-group-select`) moves the selected node between the document's groups, or out of all of them with `No group`.
- `F32.note`: **Add a note** (`project-map-add-note`) attaches a boxed note to the selected plate by a leader line and opens its editor; the box is a tab stop that reopens the editor (`project-map-edit-note-<id>`), the `×` on its corner removes it (`project-map-remove-note-<id>`), and a note with no text reads `What should a reader know?` in its place.
- `F32.collapse-group`: a group's control (`project-map-group-toggle-<id>`, `aria-expanded`, with an SVG `<title>` that says `Collapse group` / `Expand group` on hover) folds the group into one plate carrying its label and member count, and every edge that crossed its boundary arrives at the group instead, de-duplicated.
- `F32.save`: **Save map** writes the document back to `.openhands/project-map.json` (`Saving…` while it runs, then `Saved`, disabled), clears `Unsaved changes`, and the file on disk carries the new positions, pins, labels, groups and notes.
- `F32.save-error`: a write that fails leaves `The map could not be saved. The workspace may be unreachable; try again.` (`project-map-save-error`) on the page, the button back on **Save map** and the edits still in hand, and a later save succeeds.
- `F32.refresh`: **Reload from file** re-reads the document; a file whose `commit` and `generated_at` are unchanged is ignored, and a new revision read with nothing unsaved replaces the open document wholesale.
- `F32.regenerate-merge`: a new revision arriving on top of unsaved edits replays them — position, pin, hidden, group and a user-made label are carried over, the analysis's own kind, path, summary and size win, nodes it no longer reports are dropped and new ones are placed and the document stays unsaved. **Rebuild with the agent** starts the conversation that produces such a revision.
- `F32.chat-context`: the chat is a dock in the canvas's corner (`project-map-chat-dock`, `data-open`), folded until **Open chat** (`project-map-chat-dock-toggle`, `aria-expanded`; on hover, `Ask about the selection, or ask for the map itself to change`) is pressed, and **Close chat** folds it again; inside it (`project-map-chat`, under the `ASK THE AGENT` heading of `project-map-conversation`) the selection appears above the composer as removable chips (`project-map-selection-chips`), **Clear selection** empties it, and the disclosure `What the agent will be told` shows the exact message text (`project-map-context-preview`).
- `F32.chat-send`: **Start a conversation** (`project-map-send`) opens a new conversation whose first message is exactly that preview, question first, selection block second, and binds it to the dock instead of leaving the page: the pane gains the transcript (`project-map-transcript`), **Open full screen** (`project-map-open-conversation`) and **New Conversation** (`project-map-detach-conversation`), the button becomes **Send**, and later messages go into that conversation.
- `F32.intents`: **Ask about this**, **Change this** and, for a selection of routes and components only, **Redesign this** start a conversation with their own opening line, the redesign one led by `/frontend-design`, bound to the dock the same way.
- `F32.invalid`: a document the build cannot read shows `This map cannot be drawn` (`project-map-invalid`) with the reason — not JSON, not a map document, a version this build does not read, or the pointer of the offending field — and `Fix the file, or regenerate the map from a conversation.`, with **Reload from file** (`project-map-invalid-refresh`) and **Rebuild with the agent** (`project-map-invalid-regenerate`) under it.
- `F32.warnings`: a document the parser had to repair draws anyway and says what it did, one line per kind (`project-map-warning-<kind>`), counted and pluralised: dropped connections, repeated ids, undeclared groups and notes that lost their subject.
- `F32.read-error`: a file that exists but cannot be read shows `project-map-read-error` naming the absolute path it tried, and a sentence without a path when it never resolved one.
- `F32.phone`: at 390 px the canvas keeps the page with the rail folded, the header controls wrap, and nothing overflows horizontally; the rail, opened, stacks under the canvas rather than beside it.
- `F32.unsupported`: on a Cloud backend the page explains that the map is a file Canvas can only reach on a local backend, and with no backend it asks for one to be connected (`project-map-unsupported`, `data-reason` `cloud-backend` or `no-backend`); neither sends a request.

## How to get to it (user POV)

- Sidebar: **Project map** (`sidebar-map-link`), between **Customize** and **Automate**. It is hidden on a canvas locked to a Cloud host, which also has no local workspace to read.
- Command menu (`Control+k` / `Meta+k`, or `command-menu-trigger`): **Project map** in the Navigation group.
- Direct URL `/map`, and the front door: with no page pinned as home ([F02](F02-app-shell.md)) `/` redirects here, so this is what a backend opens on — `control-openhands browser goto /` lands on `/map`, and Home keeps its own URL, `/conversations`.
- The layers rather than the parts: the **View** row over the canvas (`Overview` / `Details`), offered whenever the drawing on the paper has at least two layers — the analysis's groups on **Code**, the kinds of work on **Work**. A map with more than 40 visible parts opens on `Overview` by itself and then carries **All layers** on the paper as the way back; a block opens its own layer. The work layer folds the same way, and is framed and folded again whenever it is switched to, but the hint and **All layers** are the code map's alone, so there the **View** row is the way back.
- What the agents are doing rather than what the code is: the **Map of** row (`Code` / `Work`), which changes the drawing and nothing else — no machine that opens the repository afterwards is told to start on the agents.
- The rail's contents — a feature introducing itself, anything waiting on you, the selection inspector and the legend — are behind **Details** (`project-map-rail-toggle`) in the toolbar. Clicking a part of the map opens the rail by itself, and so does a `/map` feature that has not introduced itself yet.
- Anything waiting on you, from the picture rather than the panel: a part a parked improvement cycle names wears a dot on its plate, and clicking that part opens the rail at it, where the card that answers the change is. On a map folded into its layers the dot is on the block, so the overview says which layer is waiting before anything is opened.
- Not reachable from a conversation: the map describes the repository, not a conversation, and the conversation drawer's tabs ([F08](F08-workspace-files-and-changes.md), [F27](F27-workspace-tools.md)) are views of one running agent's sandbox.
- Out of the page: nothing leaves by itself. **Generate the map**, **Rebuild with the agent**, the three intent buttons and **Start a conversation** start a conversation that stays bound to the page — in the dock, or named by the empty state's `Conversation <id> is building the map…` line — and **Open full screen** (`project-map-open-conversation` in the dock, `project-map-empty-open-conversation` in the empty state, `project-map-invalid-open-conversation` under a map that cannot be drawn once one is bound) is what goes to it ([F06](F06-agent-activity.md), [F07](F07-conversation-page.md)). Nothing on the page opens a file: the Files drawer belongs to a conversation's sandbox ([F08](F08-workspace-files-and-changes.md)) and the inspector names the path instead.
- With nothing chosen in the header's **Repository** picker (`project-map-workspace-picker`) the page reads the backend's own working directory (`workspace/project` under the agent server's home), and the picker names that folder (`data-path` and, on hover, `title`, with its last segment in the field) instead of asking `Choose a repository…` beside the map; a map read from a conversation's sandbox keeps the placeholder, and the `Workspace:` line names the conversation instead. A repository opened as a conversation's workspace ([F03](F03-home.md), [F04](F04-conversation-list.md)) is not what it draws until it is chosen there, or that conversation is bound to the page. The choice is remembered per backend (localStorage `project-map-workspace`) and survives a reload; the field's `×` (`Clear selection`) puts it down.

## Driving it with control-openhands

Preconditions:

- A run from this checkout: `export OH_VERIFY_RUN=$(control-openhands launch --new --print-run)`, then `control-openhands doctor` (`ok`) and `control-openhands onboard --skip`.
- `control-openhands fixture project-map` writes a small deterministic document (two groups, eight nodes over seven kinds, five edge kinds, one hidden node, one pinned node, a node with no summary, a node with no edges, one anchored note) to `.openhands/project-map.json` in the backend's working directory, and prints the path. `--variant regenerated|warnings|unsupported-version|invalid-field|not-json`, `--remove` and `--unreadable` reach the other states. It is an arrange step: the page's own **Save map** is what proves writing.
- Nothing on this page needs a model, but the five buttons that start a conversation (they keep the page on `/map` and bind the conversation to it) need an LLM profile to exist. With a key, `control-openhands llm preset deepseek`. Without one, `QA_FAKE_LLM_KEY=qa-not-a-real-key control-openhands llm set --profile default --model deepseek/deepseek-flash --api-key-env QA_FAKE_LLM_KEY --no-validate` is enough for the conversation to be created and carry its first message; the agent then ends in `status: error` at its first model call, so every claim about what the agent *does* with the map is `blocked`, never a pass.
- Desktop viewport (1440×1000) unless a bullet says otherwise. The `F32.phone` bullet restores it.
- The rail beside the canvas is folded on every page load, so the inspector, the legend and anything waiting on a person are not in the DOM until **Details** (`project-map-rail-toggle`) is pressed or a plate is selected. A `/map` feature that has not introduced itself opens the rail by itself, which is the state a fresh browser profile arrives in, so mark the three of them announced once before driving: `control-openhands browser eval 'localStorage.setItem("openhands-feature-trials", JSON.stringify(Object.fromEntries(["map-waiting-on-you","map-repository-picker","map-overview"].map((id)=>[id,{id,announcedAt:"2026-10-26T00:00:00.000Z"}]))))'`, then `control-openhands browser reload`. The `F32.rail` bullet drives the unannounced state and puts that ledger back.
- The chat lives in a dock in the canvas's corner that is folded on every page load. A bullet that reads the chat opens it first — `control-openhands browser click 'testid=project-map-chat-dock-toggle'`, then `control-openhands browser wait 'testid=project-map-composer' --state visible`, because the pane is loaded on demand — and the open panel covers the canvas's bottom-right corner, so those bullets come after the ones that click plates there. Reading a selection never needs it: the inspector (`project-map-inspector`, `project-map-inspector-multi`) shows the same selection.
- The marks of `F32.waiting-marks` need improvement cycles parked on this backend, and the automations version a default `launch` pins has no improve API at all (`control-openhands api GET '/api/automation/v1/improve/parked?limit=20'` is `404`), so that one bullet runs on a run of its own, launched the way [F31](F31-improvement-programs.md) launches one: `control-openhands launch --new --automation-path <automation-checkout> --print-run`, `control-openhands doctor` (`ok`), `control-openhands onboard --skip`, and `/parked` now answering `200` with `total` `0`. Arrange two cycles there the way a run reports them, one about the folder this map is of and one about another repository. `control-openhands api POST /api/automation/v1/preset/improve --write --data '{"name":"QA_F32 Improve","trigger":{"type":"cron","schedule":"0 0 1 1 *"},"improve":{"builder_profile_id":"11111111-1111-4111-8111-111111111111","repository_source":"explicit","repositories":[{"label":"QA_F32 project","url":"https://qa.invalid/qa-f32-project.git","ref":"main"},{"label":"QA_F32 Elsewhere","url":"https://qa.invalid/elsewhere.git","ref":"main"}]}}'` gives `<program-id>`; the first label carries the word `project` on purpose, because with nothing chosen in the **Repository** picker the map is of the backend's own `workspace/project` and a cycle counts only when that folder's name is in its repository label or URL. Then `control-openhands api POST /api/automation/v1/improve/<program-id>/claim --write --data '{}'` twice — in rotation order the first takes `QA_F32 project` (`<cycle-mine>`) and the second `QA_F32 Elsewhere` (`<cycle-other>`), each printing its `cycle.id` — and park each one with what it changed: `control-openhands api PATCH /api/automation/v1/improve/cycles/<cycle-mine> --write --data '{"status":"PARKED","summary":"QA_F32: moved qa/src/routes/home.tsx onto the new shell.","parked_question":"This is a breaking change. Publish it now, or wait?","parked_plan":{"breaks":["removed_export in qa/src/stores/things.ts"],"consumers":["Anything reading qa/docs for the old names."],"sequence":["Keep qa/src/api/things.ts answering both shapes for one release."],"rollback":"Revert the branch; qa/src/components/panel.tsx goes back to the old props.","branch":"qa/f32-waiting"}}'` and `control-openhands api PATCH /api/automation/v1/improve/cycles/<cycle-other> --write --data '{"status":"PARKED","summary":"QA_F32: a change in another repository, naming qa/src/hooks/use-things.ts.","parked_question":"This is a breaking change. Publish it now, or wait?","parked_plan":{"breaks":["removed_export in qa/src/hooks/use-things.ts"],"branch":"qa/f32-elsewhere"}}'`. Both are arrange, never proof: what the page draws from them is the proof.
- The work layer (`F32.work`, `F32.work-layers`) needs a deployment that answers `GET /api/automation/v1/work-graph`, and the automations version a default `launch` pins has no such route: the path falls through to `/v1/{automation_id}` and answers `422` (`uuid_parsing`), so **Work** there draws one plate — the machine itself, `External Local` — with `project-map-work-omissions` under it and no **View** row at all (`control-openhands browser count 'testid=project-map-view-switch'` is `0`, although the small fixture's two layers offer it on **Code**). Those two bullets therefore run on the run with the automation checkout, the same one `F32.waiting-marks` needs: `control-openhands launch --new --automation-path <automation-checkout> --print-run`, `control-openhands doctor` (`ok`), `control-openhands onboard --skip`, and `control-openhands api GET '/api/automation/v1/work-graph?window_days=7&limit=200'` now answering `200`. ## Gotchas

- What the page reads, in order: a folder chosen in the **Repository** picker, read on the host by its path; else the conversation the page is bound to — one its own buttons started — whose working directory is read through that conversation's runtime, the only place the file exists under a Docker sandbox (`project-map-workspace` then carries `data-conversation-id`, and `project-map-runtime-unavailable` names the conversation when its sandbox was archived, deleted or never started); else the backend's own working directory, `workspace/project` under the agent server's home with the default working dir (`control-openhands api GET /api/file/home`). A conversation started from the page is attached to the directory the page reads — the chosen folder, or the directory the map came from — so the file it writes is the one on screen, and every message the page sends names the map by its absolute path. A repository a conversation is working in is drawn only when it is chosen in the picker or that conversation is bound.
- The header says each thing once, so where a line can be read depends on what is on the page. The subtitle is a paragraph only while there is no drawing — the empty state, `project-map-loading`, `project-map-invalid`, `project-map-read-error`, `project-map-unsupported` — and over a drawn map it is the `h2`'s hover alone (`browser tooltip 'testid=project-map-page >> h2'`, which also works in the states where the paragraph is there, the `title` being unconditional). A recipe that reads `testid=project-map-page >> p >> nth=0` for it with a map open now picks up whatever prose comes next, or fails on nothing at all: with the rail and the dock folded and nothing unsaved, `testid=project-map-page >> p` counts `0`. `project-map-workspace` is rendered only when the header has no picker — a non-local backend, or a page with neither a chosen folder nor a document — or when a conversation is bound to the page, which is what it then names (`data-conversation-id`, the picker meanwhile back on `Choose a repository…`). With a local backend and a map drawn, the common case, it is absent and the folder is the picker's business: `data-path` and `title` carry the whole path, the field shows its last segment.
- The rail is folded on every page load (`project-map-rail-toggle`, `aria-expanded="false"`; the flag is not persisted), so `project-map-inspector`, `project-map-inspector-empty`, `project-map-legend` and `project-map-waiting` are not in the DOM until **Details** is pressed or a plate is selected: a `count` of `0` there is the rail, not a missing panel. A `/map` feature that has not introduced itself opens the rail by itself, so a fresh browser profile — and `browser reset` — arrives with it open and an announcement inside it; the Preconditions' one-liner marks the three announced.
- What puts a mark on a part: the parked change's own text has to contain that part's path exactly as the document spells it (`qa/src/stores/things.ts`, not `src/stores/things.ts`), and a path shorter than five characters never marks anything, because short paths match too much prose. A change naming a file the analysis never drew as a part marks nothing either; the marks are of the drawing, not of the diff. The page reads the parked list through a query that keeps its answer for 30 s, so after an `api PATCH` to a cycle, `control-openhands browser reload` rather than waiting for the page to notice.
- The counts beside each other say different things. The toolbar's `<n> waiting on you` (`project-map-rail-toggle`, `data-waiting`) counts every cycle parked on the backend, whatever repository it is about, so the run above reads `2` while only one of the two marks anything. A layer's `data-waiting` counts the marked parts the layer holds including hidden ones, while its `data-count` counts only the drawn ones: with a parked change that also names `qa/src/legacy/old.ts`, `project-map-overview-block-qa-web` reads `data-waiting` `3` and `3 parts here are in a change waiting on you.` while the opened layer shows two marks — **Show hidden nodes** draws the third, with its own mark (`control-openhands browser count 'testid=project-map-waiting-mark'` goes from `5` to `6`).
- The marks belong to the analysis's parts. **Map of** → **Work** draws the work graph instead, whose shapes are not the document's nodes, so `control-openhands browser count 'testid=project-map-waiting-mark'` is `0` there and back to its old count on **Code** — and that switch is a view like the **View** row, so the excursion leaves `project-map-unsaved` absent and **Save map** reading `Saved` (`F32.layer-switch`). The dots a folded view puts on its blocks are counted from the committed analysis's layers too, so a work layer's blocks never carry one.
- How wide the paper is depends on the rail: 1074 px with it folded and 710 px with it open, of a 1440 px window, and at the narrower width the toolbar wraps to a second row (754 px tall against 721 px). The page frames the drawing when a document arrives and **Fit to view** frames it again, both against the frame of that moment, while opening or folding the rail does not refit. So a transform, a drag measured from the canvas's centre and what a marquee catches all depend on the rail's state; the bullets above say which state they were written in, and a plate can sit outside the narrower frame entirely until **Fit to view** is pressed.
- At the framing the page opens with — the rail folded — the fixture's anchored note has its leader line on the centre of `project-map-node-qa/src/stores/things.ts`, so a plain click there answers `<path ...> from <g data-testid="project-map-note-qa-note-store"> subtree intercepts pointer events`. Click it off-centre (`browser click '...' --position 20,10`) or open the rail and **Fit to view** first, which is what the plate bullets do.
- The overview is a view, not document state: switching it refits the paper, writes nothing to the file and leaves `project-map-unsaved` absent, and a reload lets the page decide the height again (under 41 parts, the detail). It folds whichever drawing is on the paper — the committed analysis on **Code**, the kinds of work on **Work** — so the **View** row is offered whenever that drawing has at least two layers, and a work graph with one kind on it (the machine alone, which is all a default `launch` draws) is offered nothing, however many layers the file has. The folders drawn in a block are cut to its width; `data-where` carries the whole phrase, is empty for a layer with no parts — which the small fixture does not have — and is empty on every work block, those parts having no paths at all. A block's label is cut to the block's width too (`Runs whose sandbox is …`), so read the whole one from `aria-label`.
- The work layer is live and belongs to the deployments, not to the file. Its plates are keyed by what reported them (`project-map-node-oh:1/local:127.0.0.1:<port>/cycle:<uuid>`), so a literal test id carries a run's own port and a recipe reads them by prefix; its blocks are keyed by kind (`project-map-overview-block-cycle`), which is stable. The counts move between reads as work happens, and the graph is re-asked every 5 s only while a deployment reports work in flight, so assert the shape — which kinds, which lines — rather than a number that was true once. A registered backend always puts its own machine node on the graph, so the drawing is never empty and `project-map-work-empty` is not reachable while one is connected; what a deployment with no work leaves is the machine alone. The rail does not follow the paper here: a selected work plate leaves `project-map-inspector-empty` in the rail and the legend keeps listing the committed document's kinds, so a `count` of `0` on `project-map-inspector` there is the layer, not a broken selection.
- Framing is the committed map's, even when the work graph is on the paper: **Fit to view** and the **View** row's own refit both fit the document the file holds, so on **Work** they throw the drawing off the paper (the known failure on the `F32.work-layers` bullet). The framing that does follow the drawing is the one the layer switch makes, which is why those bullets switch layer rather than press **Fit to view**.
- The chat is behind the dock. `project-map-chat-dock` is folded on every page load (`data-open="false"`; the flag is not persisted) and opens by itself only when a conversation starts from this page — which in practice means never: **Rebuild with the agent**, the one launch that happens with the dock shut, is the known failure recorded on the `F32.regenerate-merge` bullet, and every other launch is made from the open pane. So `project-map-chat`, the chips, the composer, the three intents and **Start a conversation** are not in the DOM until **Open chat** is pressed, and the pane is loaded on demand: `browser wait 'testid=project-map-composer' --state visible` before using it. Open, the panel covers the canvas's bottom-right corner (448 px wide, up to 70 % of the window tall); a plate under it answers a click with `intercepts pointer events`, so fold it (**Close chat**) before clicking plates there.
- A conversation the page started is remembered with the chosen folder, per backend, in localStorage `project-map-workspace`, so a reload keeps the page bound to it — reading through that conversation, with the header picker back on `Choose a repository…` and `project-map-workspace` naming the conversation — without reopening the dock. **New Conversation** in the dock lets it go; the empty state has no such control, which is why the `F32.generate` bullet clears the key.
- On a backend whose conversations get their own container (`conversation_runtime: docker` in `server_info`), the analysis is told to write `.openhands/project-map.json` inside its own working directory instead of the host's absolute path, a chosen folder is attached to the conversation (the runtime mounts it there), and with nothing chosen the page follows the conversation's own workspace. The verify run is a host workspace, which is the absolute-path case these bullets assert.
- The buffer is keyed by the file's path, `commit` and `generated_at`. An external edit that leaves all three unchanged is invisible to **Reload from file**; only `control-openhands browser reload` picks it up. The `regenerated` fixture variant changes the commit for that reason.
- **Save map** is the only writer. Dragging, renaming, hiding, pinning, regrouping, collapsing a group and writing, editing or removing a note all only change the buffer, and leaving the page drops them without a warning. Panning and zooming are not document state and never mark it unsaved.
- Every gesture on the canvas is decided from the pointer events, because a drag captures the pointer and a captured pointer retargets the synthesised `click` at whatever holds the capture. A press and a release within 3 px is what counts as a click, on a plate and on the paper alike: `browser click` delivers one, but a `browser drag` of any real distance is a pan or a move, and it leaves the selection where it was. The paper's own click is a click on the SVG, so `browser click 'testid=project-map-canvas'` only clears the selection when the canvas's centre is empty paper — it is, in the small fixture's fitted framing, and `document.elementFromPoint` confirms it in another.
- Edge test ids join their three parts with `|` (`project-map-edge-<from>|<to>|<kind>`), so one can be typed as a `testid=` selector. Reading them all is still easier with a CSS prefix (`'[data-testid^="project-map-edge-"]'`) or `browser eval`. `browser testids` drops any element whose box has zero width or height, which an edge drawn as a perfectly straight run can reach; in the fitted framing of the small fixture the narrowest is 6 px and `browser testids --filter project-map-edge` lists all seven.
- A plate dragged to the right can end up under the rail in screen space while it is open; the next click on it fails with `<aside ...> intercepts pointer events`. Click **Fit to view** first, or fold the rail.
- `browser text` returns nothing for SVG text: the group labels, the member count on a collapsed group and the plate labels have to be read with `browser eval` on `textContent`, or through `aria-label` on the plate.
- Scope a click on an edge row or a multi-selection row to the row: `'testid=project-map-inbound >> has-text=QA_Panel'` narrows the *list*, which still matches, and clicking it hits whatever sits at the list's centre — a different node.
- `browser scroll <sel> --by N` scrolls the page, not the canvas. Zooming needs the wheel at the pointer: `browser hover 'testid=project-map-canvas'` then `browser scroll --by -300`.
- The wheel zoom is clamped to 0.25–2.5 and the drawing loses its dot grid and the plates' path lines below 0.62, so a screenshot taken while zoomed out legitimately shows fewer details than one taken after **Fit to view**.
- A note's editor is a `textarea` in a `foreignObject`, so `browser fill 'testid=project-map-canvas >> css=textarea'` reaches it and `browser text` does not: the committed text is read from `aria-label` on `project-map-edit-note-<id>`, or from the SVG `text` nodes with `browser eval`. Escape and a blur both commit it; Escape there is stopped before the canvas, so it does not clear the selection. A new note's id is generated from the clock (`note-<base36>`), so select it by prefix rather than by a literal.
- The repair notices are pluralised (`_one` / `_other`), so one dropped edge reads `1 connection pointed at a node the map does not contain, and was dropped.` A plural sentence with a count of `1` would be a regression, not a mis-read.
- A plate only carries its path line when it is tall enough (a `size` of roughly 250 lines or more) and the zoom is at or above 0.62. The fixture's `qa/src/routes/home.tsx` is the one plate big enough.
- Every button that starts a conversation fails without an LLM profile the agent profile can resolve; the page then shows two toasts, the mutation's own and the map's `The conversation could not be started. The workspace may be unreachable; try again.` — its own sentence, not the save failure's. The `F32.save-error` bullet is where that copy is driven, because an existing LLM profile cannot simply be deleted: `api DELETE /api/profiles/default` answers `409` (`LLM profile is referenced by 1 agent profile(s): default`) while the `default` agent profile points at it, so reaching the missing-profile state needs a run that never had one.
- A failed save also raises an uncaught page error (`HTTP request failed (502 Bad Gateway)`) alongside the handled `project-map-save-error` line, because the click handler drops the rejected promise. It is reproducible with `service stop agent-server` and is the one page error this family expects.
- The unsupported panel carries `data-reason` (`cloud-backend`, `no-backend`), the same handle [F30](F30-soul-settings.md)'s uses, so the two cases are told apart without reading their sentences.
- `project-map-loading` is a single frame on a local backend and is not driven here; a `/map` page that stays on `Reading the map…` means the file read is hanging, not that the state was reached.
