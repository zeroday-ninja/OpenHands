# F31 — Improvement programs

An improvement program is a cron automation that works through a list of
repositories one at a time: each run takes the next repository in the
**rotation**, has its builder agent profile research and implement one change
with cited sources, and then has every other available agent runtime review
that change adversarially. `/automations/improve/<automation-id>` is its
dashboard. It shows the rotation with the repository that is up next marked and
each repository's last verdict, then the cycle history: per cycle the
repository, a status pill, a verdict pill, the builder's runtime and
conversation, the branch, the pull request, the summary, the cited sources with
the claim each supports, every reviewer's runtime, verdict, concerns and the
sources it found stale, and any `SOUL.md` proposals the cycle made, each with an
**Add to SOUL.md** button that appends it to the user's document (F30). The
verdicts are Accepted, Changes requested, Rejected, Inconclusive, Not reviewed
by a second runtime and No change made; the last two say in words that they are
not a pass. An automation that is not a program answers 409 and the page says
so instead.

Source: `src/routes/automation-improve.tsx`, `src/components/features/automations/improve/`, `src/components/features/automations/detail/improve-program-section.tsx`, `src/hooks/query/use-improve-program.ts`, `src/types/improve.ts`, `src/utils/improve-program.ts`, `src/utils/soul-learned-preferences.ts`.

## Sub-features

- `F31.entry-point`: a program's detail page carries an **Improvement program** card whose link **View rotation and cycles** (`improve-program-link`) opens the dashboard in the same tab; an automation that is not a program has no such card.
- `F31.open`: the page shows **Back to Automations**, the automation's own name as the `h1` and the paragraph `Each run takes the next repository in the rotation, ...`; the back link returns to the dashboard.
- `F31.rotation`: the **Rotation** section lists the configured repositories in order with their position, label and ref, and marks exactly one row **Up next** (`data-up-next="true"`), the one the next run will claim.
- `F31.cycles-empty`: with no cycle yet the history reads `No cycles yet` / `The next run will claim the first repository in the rotation and record its cycle here.`
- `F31.cycle-in-progress`: a cycle that is still running shows its status pill (`Claimed`, `Building`, `Reviewing`), the verdict pill `No verdict yet` (`data-verdict="PENDING"`), `No summary reported yet.`, `No sources cited.` and `No runtime has reviewed this cycle yet.`, and the page polls the history every 5 s while it lasts.
- `F31.cycle-complete`: a finished cycle shows `Completed`, its verdict, the repository, a relative timestamp, **Built by** with the builder runtime, a **Builder conversation** link to `/conversations/<id>`, the branch, a **Pull request** link that opens in a new tab, and the summary; polling stops once the newest cycle is terminal.
- `F31.cycle-sources`: the **Cited sources** block lists each source as a link (its title, else its URL) with the claim it supports below, opened in a new tab with `rel="noopener noreferrer"`.
- `F31.cycle-reviews`: the **Adversarial review** block lists each reviewer with its runtime (`data-runtime`), its profile name when that differs, its verdict, its summary, its **Concerns** and the **Sources it found stale**.
- `F31.verdict-explanations`: `Not reviewed by a second runtime` and `No change made` each print a sentence under the pill saying this is not a pass; the other verdicts print none.
- `F31.rotation-last-verdict`: each rotation row shows **Last verdict** with the verdict of the newest cycle for that repository, and no badge for a repository whose cycles all ended without one.
- `F31.soul-suggestions`: a cycle that proposed something shows **Learned about you** with the sentence that nothing changes until the user adds one, then each proposal and the reason it was proposed; cycles with no proposal show no such block.
- `F31.soul-add`: **Add to SOUL.md** appends the proposal to the user's `SOUL.md` under a `## Learned preferences` heading with today's date, toasts `Added to your SOUL.md`, and the row turns into `In your SOUL.md` with no button, also after a reload.
- `F31.soul-read-only`: where the user's `SOUL.md` cannot be read (an agent server without the route, a Cloud backend) the block says `Your SOUL.md is not available on this backend, so these can only be read here.` and offers no Add button.
- `F31.rotation-empty`: a program whose rotation resolves to nothing replaces the section with `Nothing to work on` / `This program's rotation is empty, ...` and a **Git Sync repositories** link to `/automations/git-sync`.
- `F31.not-a-program`: `/automations/improve/<id>` of an automation without an improvement configuration shows `Not an improvement program` / `This automation has no improvement configuration, so it has no rotation or cycles to show.` and nothing else.
- `F31.not-found`: an unknown automation id shows `Automation not found` with a **Back to Automations** link.
- `F31.cycles-page`: the history shows the newest 20 cycles, newest first, and `Showing 20 of <total>` once the program has more.
- `F31.verdicts`: every verdict renders with its own label and `data-verdict` (`Accepted`, `Changes requested`, `Rejected`, `Inconclusive`, `Not reviewed by a second runtime`, `No change made`), and a failed cycle shows `Failed` with the error it reported.
- `F31.phone`: at 390 px the rotation rows and the cycle cards fit the viewport, with the badges and the Add button wrapping below the text they belong to.
- `F31.cycle-run`: a dispatched run claims a repository, implements one change on a branch and has a second runtime review it (blocked here: needs two agent runtimes with their provider keys, plus a repository the sandbox may push to).

## How to get to it (user POV)

- Sidebar **Automate** (`sidebar-automations-link`), a program's card (F21), then the **Improvement program** card's **View rotation and cycles** link on the detail page (F23 owns the rest of that page).
- Direct URL `/automations/improve/<automation-id>`.
- No command-menu entry, no sidebar entry and no Automate sub-navigation tab leads here; the sidebar keeps **Automate** highlighted while the page is open. Leave with **Back to Automations**.
- Which state appears depends on the automation, not on the user: one `GET /api/automation/v1/improve/<id>/rotation` decides (200: this family; 409: not a program; 404: unknown automation).
- Creating a program is not possible from the UI: the automation setup page (F28) and the templates (F22) offer prompt and script automations only, so a program is created through `POST /api/automation/v1/preset/improve`. Editing one needs `PUT /api/automation/v1/improve/<id>/config`; this page is read-only apart from **Add to SOUL.md**.

## Driving it with control-openhands

Preconditions:

- A run on an automation backend with the improvement API (`/api/automation/v1/improve/...`) and an Agent Server that serves `GET /api/soul`. No PyPI release has either (the pins in `config/defaults.json` answer 404), so launch both from checkouts: `export OH_VERIFY_RUN=$(control-openhands launch --new --no-browser --sdk-path <sdk-checkout> --automation-path <automation-checkout> --print-run)`, then `control-openhands browser start`, `control-openhands doctor` (`ok`) and `control-openhands onboard --skip`. Record both versions. `control-openhands api GET /api/automation/v1/capabilities --pick features` lists `presetImprove`. No LLM profile is needed: every cycle below is reported through the API, which is what a run does from inside its sandbox.
- A program with two repositories it never has to reach (the rotation is configuration, not a clone): `control-openhands api POST /api/automation/v1/preset/improve --write --data '{"name":"QA_F31 Improve","trigger":{"type":"cron","schedule":"0 0 1 1 *"},"improve":{"builder_profile_id":"11111111-1111-4111-8111-111111111111","repository_source":"explicit","repositories":[{"label":"QA Alpha","url":"https://qa.invalid/alpha.git","ref":"main"},{"label":"QA Beta","url":"https://qa.invalid/beta.git"}]}}'`. Its `id` is `<program-id>`. The yearly cron keeps the scheduler from claiming a cycle mid-recipe, and the builder profile id is a literal: in local mode the Agent Server resolves profiles at run time, so any UUID is accepted.
- An automation that is not a program, for `F31.not-a-program`: `control-openhands api POST /api/automation/v1/preset/prompt --write --data '{"name":"QA_F31 Plain","prompt":"QA fixture; never runs.","trigger":{"type":"event","source":"qa-f31","on":"qa.f31.never"}}'` (`<plain-id>`).
- A program whose rotation is empty, for `F31.rotation-empty`: `control-openhands api POST /api/automation/v1/preset/improve --write --data '{"name":"QA_F31 Empty","trigger":{"type":"cron","schedule":"0 0 1 1 *"},"improve":{"builder_profile_id":"11111111-1111-4111-8111-111111111111"}}'` (`<empty-id>`). It rotates over the organization's Git Sync repositories (F24, F29), of which a fresh run has none.
- The user has no `SOUL.md` of their own: `control-openhands api PUT /api/soul --write --data '{"content":""}'` reports `"exists": false`.
- Cycles are arranged the way a run reports them: `api POST /api/automation/v1/improve/<program-id>/claim --write --data '{}'` opens one on the next repository and prints its `cycle.id`, and `api PATCH /api/automation/v1/improve/cycles/<cycle-id> --write --data '...'` records a stage. ## Gotchas

- The page is read-only except for **Add to SOUL.md**: everything else on it is written by a run, or by the API calls that stand in for one. Creating or editing a program has no UI at all, so a recipe that needs a different rotation replaces the whole configuration with `PUT /api/automation/v1/improve/<id>/config`.
- A cycle that reached `COMPLETED` or `FAILED` is immutable (409 naming its status), so a bullet that needs another state claims a new cycle instead of patching the old one. Every claim also advances the rotation, which moves **Up next** and changes which repository the next claim takes.
- The history polls every 5 s only while the newest cycle is not terminal, and not at all while the list is empty. A bullet that waits for the page to pick up an API change needs a newest cycle in flight, or a `browser reload`.
- Test ids repeat per card, per source, per review and per proposal. Scope them by the card (`[data-cycle-id="<id>"]`), the rotation row (`[data-repository="<url>"]` or `[data-up-next="true"]`) or an `nth=`; cards are newest first, so `nth=0` changes meaning with every new cycle.
- `improve-cycle-sources` and `improve-cycle-reviews` are on every card and say in words when they are empty; `improve-cycle-soul-suggestions` is absent when a cycle proposed nothing. A missing block is not a missing section.
- A stage that reported no runtime reads `not reported` next to **Built by** or **Reviewed by**, and a reviewer's profile name is shown only when it differs from its runtime, so a card can legitimately name a runtime once.
- The `h1` is the automation's name, read from a separate request, so it can read `Improvement program` for a moment after a cold load. Wait for the rotation or the history before asserting it.
- Only twenty cycles are fetched, so the rotation's **Last verdict** is computed from those twenty: a repository whose newest verdict is older than that shows none.
- `In your SOUL.md` is decided by searching the document for the proposal's text, not by a flag: editing that line out of `SOUL.md` brings the Add button back, and a user who never had a file gets one the moment they add a proposal (the agent server's default text is kept and the bullet appended under `## Learned preferences`).
- Every Add button on the page is disabled while one proposal is being saved, and all of them stay disabled until `GET /api/soul` has answered. A `click` right after the page loads can land on a disabled button.
- 409 (not a program) and 404 (unknown automation) are expected HTTP errors that stay in `browser errors`: run `browser errors --clear` after those bullets so the family's sweep only shows surprises.
- The cited-source and pull-request links are whatever the run reported; they open in a new tab and are not reachable in a sandbox, which is why the recipes assert `href`, not the target page.
- The automation backend's own view of these routes (claim, report, rotation arithmetic, validation) is mapped by `verify-automation` F19 in `OpenHands/automation`; this family only covers what the dashboard shows.
