# F30 — SOUL.md and the identity documents

`/settings/soul` edits the user's identity: the set of documents the Agent
Server adds to the prompt of every conversation, including ACP runtimes such as
Claude Code and Codex. `SOUL.md` is the first of them; the server also declares
`STYLE.md`, `MEMORY.md`, two example files and `data/influences.md`. The page
renders one section per document the server returns, in the server's order, each
with the path it sits at, the server's own sentence about what belongs in it,
whether anything has been written, the text and a character count. Every section
is saved on its own, and emptying a written document is a clear rather than a
save — blank content is how the server is told to delete the file — so there
**Save** is replaced by **Clear document**, which says what it will do and asks
before it sends. Over 65536 characters a section refuses to send anything. On a
Cloud backend, with no backend, or on an agent server without the route the page
renders an unsupported panel instead of an error: `GET /api/soul/documents` is
optional and `compatibility.minimumAgentServer` was deliberately not raised for
it.

Source: `src/routes/soul-settings.tsx`, `src/components/features/settings/soul/`, `src/api/soul-service/`, `src/hooks/query/use-identity-documents.ts`, `src/hooks/query/use-soul.ts`, `src/hooks/mutation/use-save-identity-document.ts`, `src/hooks/mutation/use-save-soul.ts`.

## Sub-features

- `F30.open`: the settings nav lists **SOUL.md** last (`sidebar-settings-/settings/soul`) and opens a page whose header reads `SOUL.md` / `Your standing preferences, applied to every conversation`, followed by the three description paragraphs (what the document is, that the identity is a set of documents each saved on its own, and that it reaches ACP agents too).
- `F30.default-state`: the page lists one section per document the agent server declares, in the order it returns them (today `SOUL.md`, `STYLE.md`, `MEMORY.md`, `examples/good-outputs.md`, `examples/bad-outputs.md`, `data/influences.md`), each with its path, the server's sentence about what belongs in it and a `Written` / `Nothing written yet` pill matching `data-exists`, under `Stored in` and the directory the set lives in; a document nobody has written shows an empty textarea and a disabled **Save**.
- `F30.dirty-tracking`: a section's **Save** enables only while that document's text differs from what the server returned, typing the original text back disables it again, and a draft in one section leaves every other section's **Save** disabled; leaving the page discards an unsaved draft without a warning.
- `F30.save`: **Save** writes that one document (`PUT /api/soul/documents/<name>`), toasts `Your preferences were saved.`, turns its pill to `Written` (`data-exists="true"`) and leaves the other documents untouched; the textarea then shows the text as the server stored it, and it survives a reload.
- `F30.character-count`: a section's count reads `<chars> of 65536 characters` and follows every keystroke in that section only.
- `F30.over-limit`: above 65536 characters that section shows `Too long by N characters. The agent server accepts at most 65536.`, marks its textarea `aria-invalid`, disables its **Save** and sends nothing.
- `F30.empty-save`: emptying a written document replaces its **Save** with **Clear document** and says `This document is now empty. Saving it removes the file; the rest of the set is untouched.` before anything is sent; whitespace-only text counts as empty too, and a document with nothing written offers only the disabled **Save**.
- `F30.revert`: **Clear document** asks first (`Remove <path>? The agent will stop reading it, and the text you wrote will be lost.`); Cancel sends nothing, confirming toasts `The document was cleared.`, the pill is back to `Nothing written yet` and the server reports the document gone.
- `F30.command-menu`: the command menu's `SOUL.md preferences` / `Edit the standing preferences applied to every conversation.` item (`command-menu-option-soul-settings`) opens the page.
- `F30.unsupported`: on an agent server without `GET /api/soul/documents` the page shows `Not available on this backend` / `This agent server does not support SOUL.md yet. Update the agent server and try again.` (`soul-unsupported`, `data-reason="missing-api"`) and no document sections, while the nav entry stays. A Cloud backend (`data-reason="cloud-backend"`) and no backend at all (`no-backend`) use the same panel with their own sentence and send no request.
- `F30.phone`: at 390 px the heading, the description, every document section and its buttons stay inside the viewport with no horizontal overflow.

## How to get to it (user POV)

- Settings nav: the gear (`backend-selector-settings-link`) or any settings page, then **SOUL.md** (`sidebar-settings-/settings/soul`), which is the last entry on desktop and in the tablet selector; the phone hub lists it in the same place (F09 owns the nav itself).
- Command menu (`Control+k` / `Meta+k`, or `command-menu-trigger`): **SOUL.md preferences** in the Settings group.
- Direct URL `/settings/soul`.
- Not reachable from a conversation, the composer or the home page; `/settings/soul` is also unreachable on a canvas locked to a Cloud host, where the settings shell redirects to `/settings/app` (F09).
- An improvement program's **Add to SOUL.md** writes into the first document of this set (F31 owns that action); its bullets appear in the `SOUL.md` section here under a `## Learned preferences` heading.

## Driving it with control-openhands

Preconditions:

- A run whose Agent Server serves `GET /api/soul/documents`. The route is newer than the pinned release in `config/defaults.json`, so launch from a checkout of `OpenHands/software-agent-sdk` that contains it: `export OH_VERIFY_RUN=$(control-openhands launch --new --no-browser --sdk-path <sdk-checkout> --print-run)`, then `control-openhands browser start`, `control-openhands doctor` (`ok`) and `control-openhands onboard --skip`. Record the agent-server version. `control-openhands api GET /api/soul/documents` answers `200` with a `documents` array and the `directory` they live in. No LLM profile is needed: nothing on this page talks to a model.
- The user has written none of the documents at the start: every `exists` in `control-openhands api GET /api/soul/documents` is `false`. Clear any that is not with `control-openhands api PUT /api/soul/documents/<name> --write --data '{"content":""}'` (arrange, not proof).
- One backend only, which is the launch default: a second local backend adds the memory-sync block to this page (Gotchas).
- `F30.unsupported` needs a second run on an agent server without the route; it is the last bullet and launches that run itself.

## Gotchas

- The page never reports a missing route as a failure, so a `404` on an `api/soul` route in `browser errors` is the unsupported state working, not a bug. Any other failure (a 500, a dropped connection) is the `soul-load-error` panel with **Retry** (`soul-retry-button`) instead, which needs fault injection and is not mapped (see the index's "Not mapped"); the same goes for `identity-documents-none`, which only a server that declares an empty set can show.
- `compatibility.minimumAgentServer` is not raised for these routes: a backend old enough to be refused by the gate never reaches either state, and a backend new enough to pass may still answer 404.
- `identity-documents-editor` also holds a **Sync memory across backends** block (`memory-sync`), and it renders only when two or more registered backends can serve the route. A verification run with one backend never shows it, and it is not mapped.
- Every section carries the same test ids, so an unscoped `testid=identity-document-input` matches six textareas. Scope every selector to its section with `testid=identity-document-section[data-name="<name>"] >> ...`; the name is the server's id (`soul`, `style`, `memory`, `good-outputs`, `bad-outputs`, `influences`), not the path.
- The textareas are plain controlled `<textarea>`s: `browser fill` works, but writing `.value` with `browser eval` does not reach React and leaves **Save** disabled.
- A section's **Save** is disabled until its text differs from the server's, and a value re-typed to the original disables it again. Each section keeps its own draft, so an edit in one leaves the others alone — including a save, which writes one document and leaves the rest as they were.
- There is no page-wide **Save** and no **Revert to default**: the only way to delete a document is to empty its box, which swaps **Save** for **Clear document**. Both paths send `PUT /api/soul/documents/<name> {"content": ""}`, but only the clear exists in the UI, and its toast is `The document was cleared.` rather than `Your preferences were saved.`
- The 65536 limit is counted in UTF-16 units in the page while `size_bytes` from the server is UTF-8, so a document of multi-byte characters reports more bytes than the count shows.
- The server normalizes the saved text and its answer is written straight into the cache, so a textarea can change under the cursor right after Save (a trailing newline appears or disappears). Read the field after the toast, not before.
- Writing the `soul` document also invalidates `/api/soul`, which F31's **Add to SOUL.md** reads, so the two views cannot hold different text. The reverse is not true for an open page: it does not refetch after `api PUT /api/soul/documents/<name> --write`, so `browser reload` before asserting the UI.
- Toasts last a few seconds: `browser wait-text '<toast>' --timeout 5000` right after the click, or `browser toasts --history` afterwards.
- The confirmation modal's buttons are the shared `cancel-button` and `confirm-button`, and the confirm button reads `Clear document`, not `Confirm`; `browser text 'testid=confirmation-modal'` includes both labels after the message.
